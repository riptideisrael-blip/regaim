# Regaim capture, AI and media audit

Audit date: 2026-10-06. Scope: source supplied in regaim-app.zip. This is a source audit, not an assertion that Android hardware or authenticated external APIs have passed runtime tests. No code was modified during this audit.

## Summary

This is a substantial working prototype in source, not a collection of static screens. Preserve Camera2/MediaCodec/MediaMuxer, the rolling buffers, keyword audio pipe, ML Kit face watcher, local Memory model, thumbnails and existing weekly reel maker. The main gap is provenance and reliability: a trigger location is called a highlight, three stills are called video understanding, optional integrations sometimes look configured when only a key string exists, and background work is not durable.

The core loop currently is: explicitly start capture -> continuously encode into RAM -> sound/phrase/visual heuristic or manual trigger -> delay for post-roll -> publish MP4 to MediaStore -> create local JSON Memory -> optionally scan faces -> optionally ask Claude to describe 3 still frames -> UI uses the metadata. Sharing is a separate explicit operation, audited by another contributor.

## Verified source defects / gaps (not device-runtime claims)

1. **YAMNet absent in unprepared local ZIP**. LaughDetector.kt:15 expects yamnet.tflite; no asset in archive; .gitignore excludes it; CI downloads it. CaptureService.kt:544–549 catches missing model and continues camera/manual/visual recording. A local build must run preparation or produce a clear release check; compilation alone will not detect this gap.
2. **Wrong trim-relative highlight and reported duration**. ClipTrimmer seeks the previous sync frame at ClipSaver.kt:174 and records real extraction base at :185, but :220 subtracts requested startMs and :221 reports requested end-start. If requested start is not a keyframe, actual duration is longer and highlight offset is incorrect. This is directly derivable from source. Fix by using actual muxed base/end and regenerate covers/cache without replacing capture architecture.
3. **Potential data loss during asynchronous analysis**. MemoryStore.kt:151–154 passes a snapshot Memory to ClaudeClient.analyze, then replaces whole entry. If user changes favorite, title, people or privacy while request is pending, stale result overwrites those later edits. Merge analysis-owned fields into a fresh stored Memory and preserve explicit edits/provenance.
4. **Corrupt index is mistaken for empty state**. MemoryStore.kt:117–125 catches every parse/read error and returns empty list; a subsequent add uses this list and overwrites file. Temp rename at :229 is not checked. Keep backup / fail-safe read and report storage error. Do not perform Room rewrite solely for preference.
5. **Reel format compatibility incomplete**. ReelMaker.kt:156–164 checks only video MIME/size/csd-0; per-clip audio codec/config and rotation are not validated against first output track/rotation, even though recording can fall back from 48 kHz to 16 kHz. It can mux incompatible audio samples into a single track. Add validation and an understandable partial-result warning.
6. **AI summary silently falls back to raw model text**. ClaudeClient.kt:95 marks analyzed=true while description uses raw response if field blank. Validate required output fields or leave analysis retryable; never show raw JSON as story.
7. **Highlight semantics conflated**. MemoryStore.kt:49–60 stores one trigger timestamp and fallback center; there is no semantic AI selected interval. AI never writes highlightMs. Cannot label this as AI chose the best moment. Add nullable interval with source/confidence separately, migrate old marker as detection/manual origin.
8. **Every saved Memory is a video**. Only CaptureService calls MemoryStore.add. Model has no image/video kind; UI video pills and MediaMetadataRetriever presume video. No photo/video import pathway is present. Photo memories require a backward-compatible media-kind extension and picker/URI access handling.
9. **Misleading state vocabulary**. MainActivity.kt:281 and HomeActivity.kt:94 say saved while Status.pending still means post-roll not written. SettingsActivity.kt:489 says connected based solely on hasKey (string prefix), not an API handshake. Change saving versus saved and configured versus verified labels.
10. **Caches fail to invalidate on content edits**. Motion cache key is id+duration+highlight (Motion.kt:37); replacing URI with same values yields stale imagery. Day story invalidation uses only count (MemoryStore.kt:199). Include media/version fingerprint and analyzed-content signature.

## Important implementation risks requiring runtime checks

- **Timing / AV sync**: video uses dequeue-time nowUs rather than MediaCodec BufferInfo.presentationTimeUs (CaptureService.kt:513), while audio uses sample-based anchored presentation timestamps (:570–575, :657). Under load/encoder stalls this can cause drift/jitter; instrument before changing core timestamp scheme.
- **Capture stop/restart races**: stopCapture joins drain threads only 1.5/3 seconds then releases codecs and clears buffers. If thread fails to exit in time, resource conflicts are possible. Real repeated start/stop tests needed.
- **Background durability**: service START_NOT_STICKY (:150); no WorkManager/JobScheduler persistent queue. Executor jobs and pending saves disappear on process death. Six-hour wakelock expires, camera errors retry 30 times then UI remains running with error, no self-recovery guarantee. Cannot claim reliable all-day capture.
- **Long AI calls share save queue**: CaptureService saveExecutor persists clip, then scans/downloads faces and calls optional Claude (:715–745). An AI request can block later clip saves up to read timeout, with captured sample snapshots retaining memory. Separate existing save and analysis executors / durable followup without rewriting encoder.
- **Memory budget**: video ring ~37.5 MB at 6 Mbps/50 s plus AAC, previews, face crops and snapshot-retained packets; no byte-bound cutoff/backpressure. Need memory, thermal, battery and low-storage device checks.
- **Incomplete resource cleanup**: publish may leave pending MediaStore item on error (ClipSaver.kt:122–129). Temporary mux file not deleted when muxing itself fails (:58–86 before outer cleanup). ClipTrimmer resources also lack robust finally blocks. Handle rollback/cleanup.
- **Location credibility**: chooses latest cached location and accepts it without freshness/accuracy bounds (CaptureService.kt:232–236); delayed geocode occurs at save. Do not show precise place as verified when stale.
- **Recognition certainty**: face model downloaded from mutable branch without checksum (People.kt:29–59), approximate thresholds and crop-only embeddings. ML Kit face presence does not certify family identity; users need confirmation/correction. FacesScanned can become true even if extraction produced no frames (:226–253).
- **Speech privacy**: uses normal Google/service recognizer, not createOnDeviceSpeechRecognizer. Recognition can use network (KeywordSpotter.kt:220–221). Explain provider processing when enabling speech; do not claim entirely local.
- **AI provider/model availability**: external model names are constants and unverified by source audit. No authenticated request performed. Do not infer valid integration from API-key prefix. Configuration needs provider-supported model check in deployment context.
- **AI answer fidelity**: three sparse stills cannot establish who spoke, exact ending, words, or a first milestone. askMoment prompt allows family names, which weakens evidence rule. Ask must clearly distinguish stored facts from visual interpretation and unknown information.
- **Animation lifecycle**: Motion only stops on detach/isAttachedToWindow; attachment is not viewport visibility or resumed activity. Off-screen ScrollView cards or paused Activities can still decode/animate. Add lifecycle and visible-rect control, reduced-motion preference.
- **Privacy wording**: Settings says faces never leave phone (:448) while optional Claude sends frames which naturally include faces and family names (:576–578). Face embedding inference is local; recognizable family imagery can go to chosen AI provider. State this distinction accurately.

## Preserve versus improve

Preserve: capture foreground service, synchronized sample rings, keyframe-aware muxing, shared audio stream feeding speech, YAMNet wrapper, ML Kit face triggers, existing PeopleStore correction UI, bubbles, all existing explicit sharing/circle behavior, ReelMaker capability.

Low-risk product iteration: dynamic family header; a coherent Memory feed/details wrapper; source-aware 3–6 second preview around known detection marker; high-quality static fallback; honest summary states; explicit optional cloud consent; dynamic family members; visible capture mode action outside primary tab; metadata-only answers for known date/place/people when AI unavailable.

Minimally invasive engineering improvements: add media kind with default video, nullable highlight start/end/source metadata; do not change old constructors/file format incompatibly. Separate save from analysis tasks. Merge AI fields with fresh Memory. Correct ClipTrimmer timeline math. Guard unavailable model/provider paths. Cache invalidation and storage read safety. Compatibility check before reel concatenation. Model preparation documented/reproducible.

A true story-based semantic highlight scorer needs persisted detector signals with timestamps, wider temporal sampling, speech transcript if permitted, per-candidate evidence/confidence, and user feedback. Current inputs can seed it, but selecting the most meaningful story from a 60-second imported clip is not implemented. Today detection-centered preview must be named as such, and unknown highlights must not be presented as AI selections.

## Suggested real-device acceptance checks

Start from fresh install with camera/mic denied, then grant; location and notification denial must not block core recording. Start capture in foreground then screen-off; run manual/sound/phrase/visual triggers. Verify gallery clip duration, orientation, first frame, audio sync and marker position. Stop while post-roll pending. Repeat start/stop, camera taken by another app, low storage, process kill, missing YAMNet, no recognizer/network. Verify face and API absence fallback. Trim at non-keyframe offset. Build weekly reel from two same-format then mixed-rate/rotation clips. Confirm summary cannot overwrite manual edits made during pending AI request. Profile names must appear only when supplied/recognized. No hardware, API or end-to-end social runtime result is asserted by this audit.
